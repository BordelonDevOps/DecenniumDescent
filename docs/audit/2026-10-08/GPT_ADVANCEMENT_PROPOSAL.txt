2. PROPOSED advancement/acquisition rule
General rule

Class Feature Acquisition. When you gain a level in a class, use your level in that class to determine what features become available. Core class engines and explicitly scheduled class features are gained automatically. Where a class presents pools of Base, Arch, or Hero abilities without individual levels, you gain Feature Selections according to the schedule below. Feature Selections are choices, not points; they cannot be saved, transferred between classes, or spent on another class.

This avoids an extra currency while restoring the intended customization.

Ordinary Base/Arch/Hero classes

Applies to Bard, Cleric, Crimson Agent, Dragoon, Mage, Monk, Mirrorsage, Ranger, Shaman, Soldier, Thief, Tinker, Warrior and Wizard unless their explicit class table says otherwise.

1	Gain core class engine automatically. Choose 4 Base features, at least 2 Active where applicable.

This deliberately does not give every listed ability to every character. The old text promised specialization; this produces specialization without inventing Skill Points.

PROPOSED ASI/Feat default

For classes lacking an unambiguous table:

Class levels 4, 8, 12, 16, 19: choose either the existing ASI option or one eligible feat.

These are class-level milestones, not global character-level grants. If a class table already schedules them differently, its table wins. They are never additionally awarded through Feature Selections.

PROPOSED respec default

No general respec. Feature selections are permanent unless an existing class feature, feat, downtime rule, or later explicitly approved retraining rule permits changing them.

This is preferable to silently leaving respec undefined.

That is safer than inventing an oath progression.

5. What still needs design/playtest validation

The acquisition framework can be made deterministic now. The abilities themselves cannot.

With 645 path entries, 296 lacking colon-delimited descriptions, 140 explicitly DRAFT level features, and multiple slot-era/resource conflicts, the repository cannot truthfully be called a complete 1–20 campaign-playtest-ready TTRPG yet.

It can truthfully be called:

“Campaign Playtest Candidate — advancement framework and content inventory complete; mechanical normalization in progress.”

For true campaign-playtest readiness, every ability that players may select must have, at minimum:

precise effect;
action/reaction/passive classification;
range/target/area where relevant;
duration;
resource cost/generation;
save/attack formula if applicable;
frequency/cooldown/rest recovery;
scaling;
acquisition level/path;
interaction with the protected class engine.

A feature can remain flavorful or descriptive in historical sources, but it cannot be selectable in the candidate until those mechanics are deterministic.

The next completion pass should therefore be ability specification, class by class, while freezing the acquisition grammar above for testing. That is the shortest route to an actual playable campaign build without replacing the 17 class identities.
