# Finite V1 diagnostic contract for complete HC review

Proposed for actual GPT agreement. No runtime implementation or full HC acceptance. This reconciles the concrete design questions in PUBLIC_DENIAL_VOCABULARY_PROPOSAL.json; exact origin supplements retain their source and selected-branch limits. Actual GPT08 controls effective grants and revision order.

## Exact representation

Keep the existing proposed assessment/submission dispositions. The optional immutable `ExpeditionDiagnosticV1` contains a registered `ExpeditionConstraintCodeV1 Code`, a nullable `ExpeditionDiagnosticStageV1 Stage`, and `ExpeditionFactAvailabilityV1 StageAvailability`. The existing fixed per-operation fact/conditional-requirement collections remain separate; no native message, arbitrary string, source path, hidden target or private origin identifier is in this object.

The30 constraint codes and eight stage codes are exactly PUBLIC_DENIAL_VOCABULARY_PROPOSAL.json#/codes and #/proposedPublicStages. These identify host presentation, not gameplay rules. A success without a constraint has null Diagnostic; a real suspension or pending choice is described by its independently authorized continuation and is not fabricated as a failure. An actual successful transaction may separately have ProjectionUnavailable for required rich detail while preserving success. Duplicate retains its own exact receipt/current-observation meanings.

For assessment, a disclosed stage has StageAvailability=ObservedCurrent; it names the evaluated native eligibility or predicted enforcement boundary, not an executed event. For actual submission, a disclosed actual stage has StageAvailability=Immediate. A protected diagnostic always uses Stage=null and StageAvailability=Withheld, even if its internal stage is known. A technical read/projection failure can name Verification/Projection with the corresponding current/immediate availability. Do not use null to imply the native guard did not run. A later receipt explanation cannot recreate a rejected-attempt diagnostic because there is no such receipt.

The diagnostic uses one fixed object shape. Optional Stage values and StageAvailability follow this exact policy, never the number or type of hidden records. NativeEnforcementStage in a conditional descriptor is a declared future requirement, not this actual attempt stage; its protected parameters remain undisclosed. No new fact availability value or semantic state is added.

## Source identity and disclosure

The internal binding key is the exact originating native branch plus the actual selected operation/variant/profile. Matching a return string alone is insufficient. Each reviewed origin chooses a proposed code and an exact disclosure predicate. When that predicate fails, use the same registered `RequestUnavailable` code and absent protected stage for that explicitly reviewed guard. This is an intentional mapping, not a catch-all for an unimplemented origin.

Missing mappings, required bindings or implementation projection errors yield ProjectionUnavailable and fail the relevant qualification criterion until corrected. Native valid gameplay ineligibility, absent native optional records, a nonselected feature or a defensive native consistency guard must not be renamed ProjectionUnavailable simply because its native text says “Unavailable.” A real exception/candidate-validation failure remains the actual rejected execution; only its safe coarse carrier is exposed.

Whole native guards mixing private and public causes may map to RequestUnavailable as one guard. Do not split or reorder the authoritative disjuncts to manufacture a more informative reason. Continue to expose all independently authorized parameter domains, own resource costs, own current permissions, work controls, known source prerequisites and lawful alternatives. Fixed protected reasons do not waive any required known explanation or let an admitted operation disappear.

Do not falsify the actual permitted assessment/attempt disposition to make two different native outcomes compare equal. Privacy comparisons must distinguish an already-authorized coarse admissibility/transaction outcome from extra origin/cause/identity details. Where private state changes that native outcome, retain the exact source boundary for review and test that the added detail exposes no unauthorized cause; do not claim complete output equality or invent a new admission rule. Candidate generation still uses authorized public domains before native assessment, so it cannot turn hidden state into a secretly filtered identity shortlist.

Target life, willingness, conditions, custody and work details require the relevant recipient/patient/owner's current disclosure, not merely control of the initiating actor or caller-supplied target text. A source target/unavailable response cannot confirm an unknown target. Geometric explanations require every dependency of the disclosed geometric predicate to be public; visible endpoints alone do not disclose hidden occupancy, traps, observers, source effects or private reserved paths.

History/capacity and timing diagnostics are public only where the exact contributing count/amount/boundary is independently public under its field registry. Otherwise the reviewed origin maps to RequestUnavailable with no stage/counter/cause. This includes aggregate capacities, private future deadlines and caught-body/path feasibility. Published static limits and independently authorized own amounts may still be described. The new surface does not offer history deletion, extra refresh or increased limits as a remedy.

## Receipt and actual-attempt ordering

Use the effective current submission grant, including the exact existing transaction/milestone overrides. The new read fence follows endpoint/control/exposure/shape/payload checks. Fresh commands then retain original Command.ExpectedRevision before KnownTarget and native preflight. Exact retries skip fresh gameplay eligibility but require current Core authority before successful duplicate recognition. Existing host conflict behavior stays in its original place for legacy dispatch.

The exact legacy response embedded in V1 submission remains unchanged. Added receipt conflict details, old payload relationships and new facts require current pure detail authorization, including Core inventory authority where applicable. When the legacy conflict occurred before Core execution, this extra check authorizes added detail only: it cannot execute, replace the actual result, reorder the legacy attempt or claim Core was reached. The new privacy contract does not claim to sanitize fields already present in the exact embedded legacy response.

Keep primary assessment, fallback assessment, terminal-status candidate and actually executed candidate separate for automatic control. At most two native candidates were assessed and at most one executed. A protected candidate's details and stage cannot leak through row lengths or invented identifiers. Waiting without execution is not a rejected execution or receipt.

## Finite acceptance checks

Use the real contexts allocated in BRANCH_QUALIFICATION_INDEX.json. Required adversarial pairs cover malformed versus hidden targets; actor/inventory revocation versus exact retry/conflict; stale observation versus original stale command; known versus hidden occupancy; public versus hidden timing; owned versus other-owned capacity; recipient life/consent; private mining preferences; valid versus missing/foreign owning read proof; rolled-back candidate time versus committed partial contact; and primary/fallback provenance. Preserve current canonical bytes, RNG, receipts and all prohibited-call counters for reads/rejections. Compare typed/console and strict restored outputs without normalizing away IDs, absence, order or current rights.

Actual source-origin mapping, field/conditional explanation completeness and these executed checks are required for final module acceptance. This proposal requests a complete implementable contract; it does not claim those implementation proofs have already run or authorize the successor.
