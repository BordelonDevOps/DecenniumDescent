# Prowl/OpenRA architecture extraction evidence

Reviewed source pins are Prowl `e8fc2abc0e04b404fab13547676ab0a88e8e7862` and OpenRA `9636b63eaee62fcb60ef2e896e7985bdf2f1ee68`, as specified in the attached implementation handoff. This is design-pattern extraction into Decennium's existing architecture; it does not import upstream code, assets, packages, or licenses.

## Source observations

- Prowl exposes a standalone headless simulation loop in [`Game.RunHeadless`](https://github.com/ProwlEngine/Prowl/blob/e8fc2abc0e04b404fab13547676ab0a88e8e7862/Prowl.Runtime/Game.cs#L238), centralized callback registration/dispatch in [`SceneDispatcher`](https://github.com/ProwlEngine/Prowl/blob/e8fc2abc0e04b404fab13547676ab0a88e8e7862/Prowl.Runtime/GameObject/SceneDispatcher.cs#L51), and typed asset identity separated from loading in [`AssetRef<T>`](https://github.com/ProwlEngine/Prowl/blob/e8fc2abc0e04b404fab13547676ab0a88e8e7862/Prowl.Runtime/AssetRef.cs#L10) and [`AssetDatabase`](https://github.com/ProwlEngine/Prowl/blob/e8fc2abc0e04b404fab13547676ab0a88e8e7862/Prowl.Runtime/AssetDatabase.cs#L22). The extraction preserves a headless, Unity-independent Core/Persistence and Decennium's exact shared clock. Its content source IDs remain separate from Prowl-style asset GUIDs; no AssetRef equivalent or presentation asset-loading policy is added during the C# phase. Prowl's source-mount override behavior is not used for gameplay-rule resolution.
- OpenRA separates [`ActorInfo` definitions](https://github.com/OpenRA/OpenRA/blob/9636b63eaee62fcb60ef2e896e7985bdf2f1ee68/OpenRA.Game/GameRules/ActorInfo.cs#L21) from runtime [`Actor` instances](https://github.com/OpenRA/OpenRA/blob/9636b63eaee62fcb60ef2e896e7985bdf2f1ee68/OpenRA.Game/Actor.cs#L45), resolves trait construction prerequisites before instantiation ([`TraitsInConstructOrder`](https://github.com/OpenRA/OpenRA/blob/9636b63eaee62fcb60ef2e896e7985bdf2f1ee68/OpenRA.Game/GameRules/ActorInfo.cs#L94)), and separates order issue/targeting from validation and resolution ([order interfaces](https://github.com/OpenRA/OpenRA/blob/9636b63eaee62fcb60ef2e896e7985bdf2f1ee68/OpenRA.Game/Traits/TraitsInterfaces.cs#L115), [validation before resolution](https://github.com/OpenRA/OpenRA/blob/9636b63eaee62fcb60ef2e896e7985bdf2f1ee68/OpenRA.Game/Network/UnitOrders.cs#L384)). Its [`Activity`](https://github.com/OpenRA/OpenRA/blob/9636b63eaee62fcb60ef2e896e7985bdf2f1ee68/OpenRA.Game/Activities/Activity.cs#L19) distinguishes lifecycle states and cleanup, while [`HarvestResource`](https://github.com/OpenRA/OpenRA/blob/9636b63eaee62fcb60ef2e896e7985bdf2f1ee68/OpenRA.Mods.Common/Activities/HarvestResource.cs#L17) moves to a resource and rechecks harvestability there. [`PathFinder`](https://github.com/OpenRA/OpenRA/blob/9636b63eaee62fcb60ef2e896e7985bdf2f1ee68/OpenRA.Mods.Common/Traits/World/PathFinder.cs#L18) is a world spatial service. Its world tick and sync hash ([`World.Tick`](https://github.com/OpenRA/OpenRA/blob/9636b63eaee62fcb60ef2e896e7985bdf2f1ee68/OpenRA.Game/World.cs#L384)) and ordered replay recording ([`ReplayRecorder.Receive`](https://github.com/OpenRA/OpenRA/blob/9636b63eaee62fcb60ef2e896e7985bdf2f1ee68/OpenRA.Game/Network/ReplayRecorder.cs#L69)) reinforce explicit, inspectable simulation processing. These are architectural references; OpenRA's trait system, RTS clock, path metric, harvest economy, and save/replay formats are not adopted.

## Decennium application and limits

`SharedWorldConfiguration` in `Laboratory/Model/SharedWorldDefinitions.cs` separates actor/site definitions from placed instances, validates configured references and collisions before world construction, and adds scenario data to the existing fingerprint. `WorldSpatialQueries` supplies shared step and range checks used by movement and harvest-site access. Existing command discovery/query/Resolve, Authority, transactions, work ledger, domain procedures and persistence remain the authoritative route; `WorldActivityProjection` is a derived minimal active-work/conflict view, not a second saved activity ledger.

The headless case runs two configurations with distinct scenario, actor, site and finite-lot identities and placements. It checks the fixed encounter route, off-calendar travel, shared query purity, equivalent command outcomes, stale revision rejection, blocked and unreachable access, partial traversal save/restore, shared finite-stock contention, a due condition interrupt, paused-job save/load, explicit resume, successful work output with provenance/freshness/mass, carrying, and continued exploration. This validates only the currently supported numerical-warrior3 profile and fish-harvest handler. A general capability catalog, multiple general site handlers, full activity projection (progress, claims, next boundary and available lifecycle commands), and general automatic routing remain outside this slice.
